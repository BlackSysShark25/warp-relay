# Warp Relay

[English](README.md) | Русский

Warp Relay делает из дешёвого VPS ретранслятор UDP для VPN-серверов. Клиент
подключается к реле, ядро Linux через DNAT и MASQUERADE отдаёт пакеты настоящему
серверу, ответы идут обратно той же дорогой. Промежуточного прокси-процесса нет:
нечему буферизовать, нечему падать, процессор почти не занят.

Задача, под которую это писалось, простая. VPN-сервер стоит за границей, у клиентов
провайдер режет или замедляет его адрес, а второй узел в «чистом» месте решает
проблему. Порты перечисляются в небольшом текстовом файле, сторож следит, чтобы
правила и состояние ядра не разъехались после перезагрузки, смены DNS или зависшего
соединения.

```
                  :51820  ->  wg.example.com:51820              (WireGuard / AmneziaWG)
клиент -> реле    :4500   ->  engage.cloudflareclient.com:2408  (Cloudflare WARP)
                  :40000  ->  203.0.113.10:51821
```

## Установка

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/BlackSysShark25/warp-relay/main/install.sh)
```

Или склонируй репозиторий и запусти `sudo ./relay.sh`. Мастер ставит нужные пакеты
(iptables, conntrack, curl, jq, netfilter-persistent), прописывает параметры ядра,
создаёт три юнита systemd и команду `relay`, потом спрашивает первые маппинги.

Проверено на Debian 12 и 13, Ubuntu 22.04 и 24.04, с любым бэкендом iptables (nft или
legacy). Скрипт бэкенд не переключает, поэтому уживается с уже настроенными nftables,
tproxy и правилами других VPN.

## Как пользоваться каждый день

```bash
sudo relay                       # консоль: дашборд, клиенты, маппинги, сервисы, лог
sudo relay --update              # скачать свежую версию с GitHub и переустановить
sudo warp-relay-apply            # применить конфиг; можно запускать сколько угодно раз
sudo warp-relay-apply --replace  # снести все правила реле и собрать заново из конфига
relay --check-update             # сравнить установленную версию с GitHub
```

## Конфиг

`/etc/warp-relay/mappings.conf`, одна строка на маппинг. Пример с комментариями лежит в
[mappings.conf.example](mappings.conf.example).

```
# SRC_IP   SRC_PORT  DST_HOST_OR_IP               DST_PORT  LABEL
0.0.0.0    51820     wg.example.com               51820     wg-germany
0.0.0.0    4500      engage.cloudflareclient.com  2408      cloudflare-warp
0.0.0.0    40000     203.0.113.10                 51821     awg-finland
```

Первый столбец нужен только для читаемости. Правило DNAT срабатывает на любой
локальный адрес реле (`-m addrtype --dst-type LOCAL`). На машине, через которую идёт
ещё и транзитный трафик, это важно: пакеты, которые просто проходят мимо к другим
хостам на том же порту, остаются нетронутыми.

Целью может быть доменное имя. Оно разрешается при каждом применении правил и ещё раз
сторожем, поэтому переезд VPN-сервера на новый IP сводится к смене DNS-записи.

## Что делает сторож

Раз в 25 секунд он проходит по конфигу.

* У маппинга пропали правила (перезагрузили файрвол, сработал ufw, cloud-init):
  скрипт apply запускается снова.
* По маппингу шёл трафик, а счётчик FORWARD не двигается 75 секунд: записи conntrack
  для этого назначения сбрасываются. Так лечится NAT-состояние, зависшее после
  рестарта дальнего сервера.
* Маппинг, по которому трафика не было вообще, считается простаивающим. Старые
  версии принимали это за зависание и чистили conntrack по кругу, по десятку тысяч
  строк в лог за сутки. Седьмая версия так не делает.

## Conntrack и перезагрузки

UDP-туннель через NAT-реле умирает после 30 секунд тишины, если не поднять
`nf_conntrack_udp_timeout`. Записать значение в `sysctl.d` кажется достаточным, но нет.
`systemd-sysctl` отрабатывает раньше, чем загружается модуль `nf_conntrack`, ключа ещё
не существует, запись пропускается с одной строкой в журнале, которую никто не читает,
а модуль потом поднимается с заводскими значениями. На работающей машине всё выглядит
нормально, потому что кто-то когда-то руками выполнил `sysctl --system`. После
следующей перезагрузки туннели снова начинают отваливаться.

В седьмой версии это закрыто с трёх сторон: `nf_conntrack` прописан в `modules-load.d`
и грузится до sysctl, небольшой юнит повторно применяет файл после поднятия сети, и сам
скрипт apply выставляет значения. Проверить любую машину:

```bash
journalctl -b -u systemd-sysctl | grep "Couldn't write"
```

Пустой вывод и есть правильный ответ.

## Cloudflare WARP

Мастер умеет добавить маппинг `relay:4500 -> engage.cloudflareclient.com:2408`. Порт
2408 у WARP отвечает за данные WireGuard. Переброс на 4500 со стороны Cloudflare
просто не отвечает, и ранние версии жили с этой ошибкой довольно долго. В клиенте WARP
или WireGuard укажи `Endpoint = ip-реле:4500`.

## Что ставится в систему

| Путь | Назначение |
|---|---|
| `/usr/local/bin/relay` | этот скрипт в режиме консоли |
| `/usr/local/bin/warp-relay-apply` | применяет конфиг; каждое правило сначала проверяется, потом добавляется, дублей не бывает |
| `/usr/local/bin/warp-relay-watchdog` | цикл сторожа |
| `/etc/warp-relay/mappings.conf` | твои маппинги |
| `/etc/sysctl.d/90-warp-relay.conf`, `/etc/modules-load.d/warp-relay-conntrack.conf` | параметры ядра |
| `warp-relay-sysctl-reapply.service`, `warp-relay-apply.service`, `warp-relay-watchdog.service` | порядок загрузки: модуль, sysctl, правила, сторож |
| `/var/log/warp-relay.log` | лог, дублируется в journald |

Удалить: `relay`, пункт Services, Uninstall, потом `rm -rf /etc/warp-relay`.

## Обновление

`sudo relay --update` скачивает `relay.sh` из этого репозитория, проверяет, что файл
разбирается без ошибок, заменяет `/usr/local/bin/relay` и даёт новой версии пересоздать
свои вспомогательные скрипты и юниты. Твой `mappings.conf` не трогается.
`relay --check-update` только сравнивает версии.

## Похожие проекты

[arblark/cascad](https://github.com/arblark/cascad) делает DNAT-проброс для TCP и UDP
из меню на bash, с IPv6 и BBR, но без сторожа, доменных имён в качестве целей и
описанного выше фикса conntrack. [zhboner/realm](https://github.com/zhboner/realm) и
[ginuerzh/gost](https://github.com/ginuerzh/gost) работают в пространстве пользователя:
возможностей больше, но в пути данных появляется процесс.

## Приватность

Экран «Connected clients» отправляет адреса клиентов на ip-api.com по обычному HTTP,
чтобы показать страну и провайдера. Больше ничего с машины не уходит. Не хочешь этого,
просто не открывай этот экран.
